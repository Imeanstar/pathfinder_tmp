# Cloud Run 배포 가이드 (Task 6-2)

1차 프로젝트("내돈예산")를 같은 부트캠프 공용 GCP 프로젝트에 배포하며 겪은 문제 2가지를
미리 반영했다 — 상세: `../프로젝트/포트폴리오_내돈예산_백민우.md` Part 9.2.

- **GitHub 연동(Developer Connect)으로 배포 시도하면 IAM 권한 부족으로 403 에러.**
  부트캠프 공용 프로젝트라 서비스 계정 IAM을 직접 못 바꾼다 → 아래처럼
  **`--source .`(소스 직접 업로드, Cloud Build가 대신 이미지를 빌드)** 방식만 쓴다.
  이 방식은 로컬에 Docker가 없어도 된다(Cloud Build가 서버에서 빌드).
- **API 키를 평문 환경변수로 등록했다가 나중에 발견.** 이번엔 처음부터 Secret Manager로
  등록한다(`GOOGLE_API_KEY`, `EMAIL_HASH_PEPPER`). `GOOGLE_OAUTH_CLIENT_ID`는 원래
  프론트(`/api/config` 응답)로 그대로 노출되는 공개 값이라 비밀이 아님 — 일반 env var로
  등록해도 무방하다.

## 0. 사전 준비

Cloud Shell은 열 때마다 빈 환경이라(로컬 머신이 아님) 저장소가 없다 — 아래 명령을
전부 Cloud Shell 터미널에 순서대로 입력한다. 이후 모든 단계는 클론한 저장소
디렉터리(`ajou-pathfinder`) 안에서 실행하는 것을 전제로 한다.

```bash
gcloud --version   # Cloud Shell엔 이미 설치·인증돼 있음(로컬에서 할 때만 아래 두 줄 필요)
# gcloud auth login
gcloud config set project <부트캠프 공용 GCP 프로젝트 ID>

git clone https://github.com/minu-dev/ajou-pathfinder.git
cd ajou-pathfinder
```

## 1. 비밀값을 Secret Manager에 등록

`.env`에 있는 실제 값을 그대로 쓴다(터미널 히스토리에 평문이 남는 게 싫으면 파일에서
읽어서 넘기는 아래 방식을 그대로 써도 됨 — `--data-file=-`로 stdin에서 읽음).

```bash
gcloud services enable secretmanager.googleapis.com

printf '%s' "$(grep '^GOOGLE_API_KEY=' .env | cut -d= -f2-)" | \
  gcloud secrets create GOOGLE_API_KEY --data-file=- --replication-policy=automatic

printf '%s' "$(grep '^EMAIL_HASH_PEPPER=' .env | cut -d= -f2-)" | \
  gcloud secrets create EMAIL_HASH_PEPPER --data-file=- --replication-policy=automatic
```

이미 만든 시크릿 값을 바꿔야 하면 `create` 대신 `gcloud secrets versions add <이름> --data-file=-`.

시크릿을 새로 만들면(`create`) Cloud Run 서비스 계정에 접근 권한이 자동으로 없다 —
3단계 배포에서 `Permission denied on secret ... Secret Manager Secret Accessor role`
에러로 나타난다(실제로 겪음, 2026-08-22 — `GOOGLE_API_KEY`는 1차 프로젝트 때 이미
권한이 부여돼 있어 안 걸렸지만, 새로 만든 `EMAIL_HASH_PEPPER`에서 걸렸다). 새 시크릿을
만들 때마다 아래로 권한을 부여한다:

```bash
PROJECT_ID=$(gcloud config get-value project)
SA="$(gcloud projects describe "$PROJECT_ID" --format='value(projectNumber)')-compute@developer.gserviceaccount.com"

gcloud secrets add-iam-policy-binding GOOGLE_API_KEY \
  --member="serviceAccount:$SA" --role="roles/secretmanager.secretAccessor"
gcloud secrets add-iam-policy-binding EMAIL_HASH_PEPPER \
  --member="serviceAccount:$SA" --role="roles/secretmanager.secretAccessor"
```

## 2. Firestore 활성화(로그인 계정별 최신 로드맵 저장소)

`app/user_store.py`가 Firestore를 기본 저장소로 쓰고, 인증정보가 없는 로컬 개발에서만
SQLite로 조용히 대체된다(2026-08-21 재설계). Cloud Run 컨테이너는 무상태라 SQLite만
쓰면 재배포·스케일다운 때 데이터가 사라지므로, 배포 전 Firestore를 켜야 한다.

```bash
gcloud services enable firestore.googleapis.com

# 이 GCP 프로젝트에 Firestore 데이터베이스가 아직 없으면 하나 만든다(최초 1회만).
# 이미 있으면 이 명령은 에러가 나는데, 무시하면 된다.
gcloud firestore databases create --location=asia-northeast3
```

Cloud Run의 기본 서비스 계정(Compute Engine default service account)이 Firestore
읽기/쓰기 권한이 없으면 아래로 부여한다(부트캠프 공용 프로젝트라 이미 Editor 역할이면
보통 필요 없다 — `403`/`PermissionDenied`가 나올 때만 실행):

```bash
PROJECT_ID=$(gcloud config get-value project)
SA="$(gcloud projects describe "$PROJECT_ID" --format='value(projectNumber)')-compute@developer.gserviceaccount.com"
gcloud projects add-iam-policy-binding "$PROJECT_ID" \
  --member="serviceAccount:$SA" --role="roles/datastore.user"
```

## 3. 배포

```bash
gcloud run deploy ajou-pathfinder \
  --source . \
  --region asia-northeast3 \
  --allow-unauthenticated \
  --memory 1Gi \
  --max-instances 5 \
  --set-env-vars GOOGLE_OAUTH_CLIENT_ID=<발급받은 클라이언트 ID> \
  --set-secrets GOOGLE_API_KEY=GOOGLE_API_KEY:latest,EMAIL_HASH_PEPPER=EMAIL_HASH_PEPPER:latest
```

처음 실행하면 Cloud Run 서비스 계정에 Secret Manager 접근 권한을 자동으로 요청하는
프롬프트가 뜰 수 있다 — 승인(`y`)하면 된다. 완료되면 `https://ajou-pathfinder-xxxxx-an.a.run.app`
형태의 URL이 출력된다.

## 4. 배포 직후 반드시 해야 하는 것 — OAuth 클라이언트에 배포 주소 등록

지금 OAuth 클라이언트(`783601922022-n6g99...`)엔 `http://localhost:8000`/
`http://127.0.0.1:8000`만 등록돼 있다. **배포된 주소를 추가로 등록하지 않으면 로그인이
로컬에서만 되고 배포본에선 그대로 `no registered origin` 에러가 난다**(우리가 겪었던 것과
똑같은 에러).

1. Google Cloud Console → API 및 서비스 → 사용자 인증 정보 → 해당 웹 애플리케이션 클라이언트
2. "승인된 자바스크립트 원본"에 방금 나온 Cloud Run URL을 정확히 추가(`https://` 포함,
   끝에 슬래시 없이) → 저장

## 5. 확인

```bash
curl https://<배포된 주소>/health
# {"status":"ok","guardrail_enabled":true} 가 나와야 정상
```

브라우저로 배포된 주소에 접속해 로그인·업로드·로드맵→[내 로드맵 이어보기](재접속해도
같은 계정이면 유지되는지)까지 한 번 실제로 돌려본다.

Firestore가 실제로 쓰이고 있는지는 GCP 콘솔 → Firestore → 데이터 탭에서
`user_plans` 컬렉션에 문서가 쌓이는지로 확인할 수 있다. 만약 여기 아무것도 안 쌓이고
"이어보기"가 재배포할 때마다 초기화된다면 Firestore 연결이 실패해 SQLite 대체 경로로
빠지고 있다는 뜻 — Cloud Run 로그(`gcloud run services logs read ajou-pathfinder`)에서
Firestore 관련 예외가 없는지, 위 2단계의 IAM 권한이 실제로 부여됐는지 확인한다.

## 참고 — 로컬 개발에서는 여전히 SQLite

`app/user_store.py`는 Firestore를 먼저 시도하고, 실패하면(로컬엔 GCP 인증정보가 없어
항상 실패함) 조용히 로컬 SQLite(`data/user_plans.db`)로 대체한다. 로컬에서 `uvicorn`으로
띄워 테스트할 땐 이게 정상 동작이다 — Cloud Run에 배포됐을 때만 Firestore를 실제로 쓴다.
