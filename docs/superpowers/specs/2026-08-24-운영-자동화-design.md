# AJOU Pathfinder 운영 자동화 — 설계 스펙

> 작성일: 2026-08-24 · 상태: 승인됨(브레인스토밍 완료) · 다음 단계: 계층별 구현

## 0. 목적과 제약

**목적**: 최종 프로젝트(08/24~25) 고도화 주제. "서비스가 조용히 틀려지는 3가지 경로"를 자동으로
감지·차단한다.

**제약**:
- ~~**GCP 권한 없음**~~ **(2026-08-24 정정)** — 최초 설계 시점엔 부트캠프 공용 GCP 프로젝트라
  서비스 계정 IAM을 직접 못 바꾼다고 가정했다(`docs/배포.md`에 실제로 겪은 Developer Connect
  403 기록됨, 그래서 계층 1~3은 자동 배포 없이 GitHub Actions 무료 러너 안에서 완결되도록
  설계했다). 이후 실제로 `gcloud projects get-iam-policy`로 확인한 결과 **Owner 역할**을
  갖고 있었다 — Developer Connect 403은 IAM 권한 부족이 아니라 그 기능 자체의 별도 제약
  (GitHub App 조직 설치 등)이었던 것으로 보인다. Owner라면 Workload Identity Federation
  구성에 필요한 모든 권한을 갖고 있어, 4장 이후 CD(계층 4)를 추가했다.
- **2일 스프린트** — 계층 단위로 독립적으로 잘라낼 수 있어야 한다. 시간이 부족하면
  계층 3 → 2 순으로 버려도 계층 1만으로 이야기가 완결돼야 한다.
- **비밀값 최소화** — 계층 1~3은 전부 GOOGLE_API_KEY 등 시크릿 없이 동작한다(테스트는 API 키
  없는 "개발 모드" 경로를 그대로 타고, 아주허브 태깅은 규칙 기반, 요람 다운로드는 인증
  불필요한 공개 게시판). 계층 4(CD)는 배포 자체가 목적이라 예외적으로 GCP 인증이 필요하지만,
  서비스 계정 키(JSON) 대신 Workload Identity Federation(키 없는 방식)을 썼다.

## 1. 문제 정의 — 서비스가 조용히 틀려지는 3가지 경로

| # | 경로 | 지금 상태 | 실제로 겪었나 |
|---|---|---|---|
| 1 | 코드 변경이 판정 로직을 깨뜨림 | pytest 292개는 있지만 사람이 기억해서 돌려야 함 | 위험만 존재 |
| 2 | 학교 데이터(아주허브·요람)가 바뀌었는데 카탈로그는 그대로 | 아무도 모름 | 과목명 개편 6쌍을 수동 발견 |
| 3 | 배포본이 코드와 다른 상태 | 사용자가 먼저 발견 | ✅ 실제 발생(2026-08-23, 남은학기 버그) |

3계층 자동 감시망으로 각각 대응한다. 계층은 독립적이며, 자동 배포는 하지 않고
**"사람이 확인해야 할 신호"를 자동으로 만드는 것**까지가 범위다.

## 2. 계층 1 — 코드 회귀 방지 (`ci.yml`)

**트리거**: `push`(main), `pull_request`, `workflow_dispatch`(수동).

**검증된 사실**(2026-08-24, `git archive HEAD`로 실제 CI 체크아웃을 재현해 확인):
`.env` 없는 깨끗한 체크아웃에서 `pytest -q` 292개 전부 통과. API 키 없는 "개발 모드" 경로가
실제로 안전하게 동작함을 재확인했다.

**Job A `test`**
- Python 3.12(배포 타겟 `Dockerfile`의 `python:3.12-slim`과 동일 버전)
- `pip install -r requirements.txt`
- `pytest -q` — 292개 전부 통과해야 함

**Job B `container`**
- `docker build -t ajou-pathfinder .`(레포 루트 `Dockerfile` 그대로 사용)
- 컨테이너를 실제로 띄우고 `curl -f http://localhost:8080/health` 로 200 확인
- **이 Job이 핵심인 이유**: `requirements.txt`(개발)와 `requirements-runtime.txt`(런타임)가
  분리돼 있어 "로컬 테스트는 통과하는데 배포만 깨지는" 구조적 위험이 있다(실제로
  `google-cloud-firestore`/`google-genai` protobuf 버전 충돌을 겪었다, `docs/배포.md` 참고).
  `docker build`만으로는 부족하고 — 실제로 띄워서 import 에러·설정 누락을 잡아야 한다.

## 3. 계층 2 — 데이터 신선도 (3갈래)

| 대상 | 방식 | 자동화 수준 |
|---|---|---|
| 아주허브 프로그램 | NCR ID 순차 스캔 + 규칙 기반 태깅 | 실제 신선도 유지 → auto PR |
| 요람 PDF | 게시판에서 최신 연도 게시글 탐색 → 직접 다운로드 | 실제 신선도 유지 → auto PR |
| 교육과정 JSON(`graduation_requirements.json`) | 하드코딩(`02_build_curriculum.py`)이라 자동 변환 불가 | 검증만 — 새 요람 PDF 도착이 "사람이 재대조하라"는 신호 |

### 3.1 아주허브 프로그램 (`ajouhub-freshness.yml`)

**검증된 사실**: `01_fetch_programs.py`는 하드코딩이 아니라 NCR ID(`getProgramDetail.do?npiKeyId=NCR{12자리}`)
순차 스캐너다. **기존 결과를 유지한 채 병합**한다(`by_id = {p["id"]: p for p in existing}`) —
재실행해도 안전(멱등). 현재 카탈로그는 ID 2000~2298(282건) 커버.

`03_tag_competency.py`는 **규칙 기반(키워드 매칭)** — LLM/API 키 불필요, 재실행해도 항상
같은 태그(멱등).

**흐름**:
```
주 1회(월요일) + 수동 트리거
  ↓
현재 programs.json의 최대 ID 확인(2298)
  ↓
01_fetch_programs.py --start 2299 --end 2499   (기존 0.7초 간격 유지)
  ↓
03_tag_competency.py                            (규칙 기반, 시크릿 불필요)
  ↓
programs.json 변경 있으면 → auto PR (본문에 "신규 N건: 제목 목록")
  ↓
사람이 리뷰 후 머지                              (자동 머지 아님 — 의도적 설계)
```

**"자동 머지가 아니라 자동 PR"인 이유**: 새로 발견된 프로그램의 역량 태그는 규칙 기반이라
오분류 가능성이 있다. 완전 자동 반영 대신 사람이 최종 확인하게 두는 것 — Responsible AI
축과 연결되는 설계 근거.

**한계(명시)**: ID가 계속 순차 증가한다는 가정(Phase 0 스파이크로 검증됨)이 깨지면(학교가
ID 체계를 바꾸면) 이 설계는 재검토가 필요하다.

### 3.2 요람 PDF (`yoram-freshness.yml`)

**검증된 사실**(2026-08-24 실측):
- 게시판: `https://www.ajou.ac.kr/kr/bachelor/bulletin.do?mode=list&srCategoryId=355`
  (소프트웨어융합대학 카테고리)
- **직접 다운로드 링크** 존재: `?mode=download&articleNo={번호}&attachNo={번호}` — 상세페이지를
  거칠 필요 없음
- 제목에 연도 포함: "2026학년도 소프트웨어융합대학 소프트웨어학과" 형식
- 목록이 **최신순 정렬**(1페이지에 이미 2026학년도 존재) — 페이지네이션 순회 불필요, 1페이지만
  확인하면 됨
- 게시글 자체엔 작성일이 표시되지 않음 — 제목의 "N학년도" 문자열만으로 신규 여부 판정
- **robots.txt 확인 결과**: `www.ajou.ac.kr`은 ClaudeBot·CCBot·GPTBot 등 AI 크롤러를 이름으로
  명시적으로 차단하고(`Disallow: /`), `User-agent: *`는 허용한다. 사용자에게 이 사실을
  공개하고 확인받은 뒤 진행하기로 결정함(2026-08-24) — 일반 UA(`Mozilla/5.0`, 기존
  `01_fetch_programs.py`와 동일 패턴)로 자동화하며, 요청 빈도는 연 1회뿐이라 부하 영향은
  무시할 수준.
- `요람/` 폴더는 저장소 루트에 실제로 git 추적 중(2021~2026 PDF 6개, `요람/{연도} 요람.pdf`
  형식)

**흐름**:
```
연 1회 + 수동 트리거
  ↓
게시판 1페이지에서 "소프트웨어학과" 포함 제목 중 최신 연도 추출
  ↓
요람/{연도} 요람.pdf 존재 여부 확인
  ↓
없으면 → mode=download 링크로 직접 다운로드 → 요람/{연도} 요람.pdf 로 저장
  ↓
auto PR (본문에 "⚠️ 새 학년도 요람 도착 — graduation_requirements.json 수동 갱신 필요" 명시)
  ↓
사람이 PDF 대조해 JSON 수동 갱신 후 머지
```

## 4. 계층 3 — 배포본 감시 (`smoke.yml`)

**선행 코드 변경 1건 필요** — `/health`에 빌드 SHA 노출:
- `Dockerfile`: `ARG GIT_SHA` → `ENV GIT_SHA=$GIT_SHA`
- `app/api.py`: `/health` 응답에 `"version": os.environ.get("GIT_SHA", "unknown")` 추가
- 배포 명령에 `--set-env-vars GIT_SHA=$(git rev-parse --short HEAD)` 추가(`docs/배포.md` 갱신)

**검증된 사실**(2026-08-24 실측, 배포 URL:
`https://ajou-pathfinder-783601922022.asia-northeast3.run.app`):
- `/health` 200 확인됨, **콜드스타트 17.7초** 실측 — 스모크 테스트 타임아웃은 60초로 설정
- 배포본이 `term_calendar_labels` 필드와 과목명 동등성(1fa0951) 판정 결과를 갖고 있어
  **현재 배포본은 최신 상태**임을 API 응답으로 직접 검증(코드 리딩이 아니라 실제 HTTP 응답
  대조)

**검사 항목**(6시간마다 + 수동):
1. `/health` 200 + `status=="ok"`
2. **버전 드리프트** — 배포본 `version`(SHA) vs main 최신 SHA → 다르면 "배포 안 됨" 경보
   (GitHub Issue 자동 생성)
3. `/api/config` 200 + `tracks` 8개 확인
4. **Gemini 쿼터·장애**(2026-08-24 추가) — `GET /api/diagnostics/gemini` 신설.
   최소 호출("ping")로 실제 응답 여부를 확인한다. 이게 필요했던 이유: 기존 3개 검사가
   전부 정상이어도 Gemini 쿼터 초과는 못 잡았다 — `/api/upload`(성적표 구조화)는
   `default_structure_fn`에 예외 처리가 아예 없어 처리 안 된 예외가 500까지 새어나가고,
   `/api/plan`이 부르는 `soften_recommendation_reasons`(추천 사유 자연어화)는 반대로
   실패를 조용히 삼켜(의도된 설계, 장식용 문구라 폴백해도 안전) 겉으로는 정상처럼 보인다.
   스모크 테스트가 실제로 이 둘 중 어느 경로도 태우지 않아 쿼터 초과 상황 자체를 볼
   방법이 없었다 — 전용 진단 엔드포인트로 메꿨다.
5. `/api/plan` 실제 호출(21학번 샘플 성적표) → `roadmap.schedule` 생성 확인

## 4-1. 계층 4 — CD (`deploy.yml`)

**추가 배경**(2026-08-24): 원래 설계는 "GCP 권한 없음"을 전제로 계층 1~3까지만 다뤘는데,
실제로 `gcloud projects get-iam-policy`로 확인한 결과 Owner 역할이 있었다. 진짜 CI/CD(검증
통과 → 자동 배포)를 완성하기 위해 계층 4를 추가했다.

**인증 방식**: 서비스 계정 키(JSON)를 GitHub 시크릿으로 저장하는 대신 **Workload Identity
Federation**(키 없는 방식)을 썼다 — GitHub Actions가 실행될 때마다 짧은 수명의 OIDC 토큰만
받아 GCP 서비스 계정을 대리(impersonate)한다. 장기 유효한 키가 저장소 어디에도 남지 않는다.

**GCP 쪽 설정**(Cloud Shell에서 1회, 사람이 직접 — 저장소 범위로 제한):
- 배포 전용 서비스 계정 `github-actions-deployer` 신설, 역할 4개(`run.admin`,
  `iam.serviceAccountUser`, `cloudbuild.builds.editor`, `storage.admin`) 부여
- Workload Identity Pool + Provider(GitHub OIDC) 생성, `attribute-condition`으로
  `minu-dev/ajou-pathfinder` 저장소로만 범위 제한
- 그 서비스 계정을 이 저장소가 대리할 수 있게 `workloadIdentityUser` 바인딩

**GitHub 쪽 설정**: `WORKLOAD_IDENTITY_PROVIDER`·`SERVICE_ACCOUNT_EMAIL`을 repository
variable로 등록(시크릿 아님 — 실제 인증 주체는 OIDC 토큰이라 이 값들은 식별자일 뿐).

**흐름**:
```
push to main
  → ci.yml 실행(pytest + 컨테이너 헬스체크)
  → 성공?
      예 → deploy.yml 자동 트리거(workflow_run) → WIF 인증 → gcloud run deploy
           (GIT_SHA 포함) → 배포 직후 즉시 smoke_test.py 실행(계층 3 재사용)
      아니오 → 배포 자체가 안 일어남
```

**실전에서 겪은 것**: Cloud Shell에 여러 줄(백슬래시 연속) 명령을 한 번에 붙여넣다가
파이프가 꼬여 명령 2개가 섞이는 사고가 있었다 — 이후로는 모든 gcloud 설정 명령을 한 줄로
바꿔 순서대로 하나씩 실행하도록 안내를 바꿨다.

## 5. 발표 데모 시나리오

1. **계층 1** — 일부러 테스트 깨는 커밋 푸시 → 🔴 → 되돌리면 🟢
2. **계층 3** — 배포 없이 커밋만 푸시 → 버전 드리프트 경보 🔴 → 재배포 → 🟢
3. **계층 2** — 수동 트리거 → 아주허브/요람 신선도 리포트, auto PR 생성 확인
4. **계층 4** — 평범한 커밋 푸시 → CI 통과 → **사람 개입 없이** 자동 배포 → 배포 직후
   스모크 테스트까지 한 번에 실행되는 것을 실시간으로 시연

## 6. 구현 순서

1. **계층 1** — `ci.yml` (test + container job) — 가장 확실, 먼저 확보
2. **계층 3** — `/health` 확장(`GIT_SHA`) + `smoke.yml`
3. **계층 2** — `ajouhub-freshness.yml` → `yoram-freshness.yml`
4. **계층 4** — WIF 설정(Cloud Shell) + `deploy.yml`
5. 데모 리허설 + 발표자료

## 7. 명시적으로 하지 않는 것 (YAGNI)

- 서비스 계정 키(JSON)를 GitHub 시크릿으로 저장하는 방식 — WIF가 더 안전해 대신 채택
- Slack/이메일 알림 — GitHub Issue로 충분
- 커버리지 게이트, 이미지 취약점 스캔, 린트 강제
- 요람 PDF 내용 자동 파싱(`graduation_requirements.json` 자동 갱신) — `02_build_curriculum.py`가
  하드코딩 구조라 이번 스프린트 범위 밖. 계층 2는 "새 PDF가 도착했다"까지만 자동화한다.
- 아주허브 프로그램 삭제(폐지) 감지 — `01_fetch_programs.py`가 병합만 하고 제거하지 않는
  기존 동작을 그대로 따른다. 만료된 프로그램은 이미 로드맵에서 `is_precedent` 플래그로
  처리되고 있어 별도 정리가 급하지 않다.
